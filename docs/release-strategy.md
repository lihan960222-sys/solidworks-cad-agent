# 发布方式评估：代码仓库为主体，Skill 为后续入口

## 建议

当前发布为 **可复现实验代码仓库 + 工作流文档**，待跨案例输入和恢复机制稳定后，在同一仓库增加薄层 Skill。若面向非开发者分发，再考虑把 Skill 与可用连接器包装成插件。三者不是互斥选项，而是不同层次。

| 形式 | 当前适配度 | 价值与限制 |
|---|---|---|
| 代码仓库 | 最适合当前阶段 | 版本管理、差异审阅、离线测试、迁移说明和失败复盘；使用者仍需配置 Windows/SolidWorks |
| 单独 Skill | 目前不宜替代仓库 | 易被 Agent 发现和调用，适合描述输入、步骤、停止条件；但指令本身不能替代 COM、模板、许可证与几何验证代码 |
| 仓库 + Skill | 推荐下一阶段 | 同一套执行代码接受不同模型调用，Skill 提供清晰使用契约；避免把全部代码和历史对话塞进提示词 |
| 插件 | 后续面向安装分发 | 能组织 Skill 和连接器；增加配置、兼容性、权限和发布维护成本，现在没有必要先做 |

官方说明中，Skill 是 `SKILL.md` 加可选脚本/参考资料的目录；Codex 按名称和描述发现它，需要时读取指令。Skill 可以放进代码仓库，不必另建一个排斥代码的产品。面向可安装分发，官方文档进一步建议插件包装。[OpenAI：Build skills](https://learn.chatgpt.com/docs/build-skills)

## 为什么现在不直接打包成“一个 Skill 就能做 CAD”

本次静态装配确实通过，但执行器仍有特定零件前缀、固定基准和目录命名约定；图纸数据整理仍依赖工程判断；复杂曲面未达到精确复现；原生特征不一定全部完成设计意图约束。把这些脚本套上 SKILL.md 不会消除这些边界。

不应把成功归因于一段神奇提示词。能力来自模型推理、经整理的输入、脚本、SolidWorks 内核与验证闭环共同作用。更换推理模型可能改变读图、分解、选择与恢复质量，但不应改变执行器的单位、输入契约与验收标准。

## 后续 Skill 应包含什么

只描述：适用/不适用场景、输入模式、源模型授权、单位和坐标系、已安装执行器的调用方法、暂停条件、逐阶段验收与失败证据保存。具体尺寸留在案例输入；几何操作留在代码；经验放分主题参考资料。

避免：绑定某个法兰/机械手的固定步骤，默认读取原件，默认允许覆盖文件，把原始对话全文当说明，把欠约束或未检查项标为通过。

后续需先用不同案例验证，再在必要时比较不同模型；此次按用户要求不进行新测试、不创建 Skill。

## 对外名称与声明

建议名称：**SolidWorks CAD Agent — 图纸辅助建模与静态装配验证工具集（实验版）**。

可以说：已验证指定案例中的原生参数化建模操作、几何比较及多零件静态配合；记录了失败与修正。

不能说：任意 PDF 自动还原、工业级全自动设计、通用装配 100% 成功、已验证跨模型/跨版本兼容、模型可直接生产。

## 许可证

当前仓库没有 LICENSE 文件。建议发布者明确选择代码许可，并单独审查工业案例、外部图纸和供应商模型的再分发权。此次不替用户决定 MIT/Apache-2.0/其他许可，也不上传相关模型或图纸。引用上游项目不等于可以复制上游源码；当前仅保留链接和客户端代码。
